# Rule 64-4.221 requirements matrix

MMTC Seed-to-Sale Tracking System Integration. Adopted 8-24-26. Transcribed from
the adopted rule document (see `docs/sources.md`).

| ID | Citation | Requirement | Product implication | Enforced by |
|---|---|---|---|---|
| STS-1 | 64-4.221(2) | The internal STS must fully integrate with the department STS, defined as connecting and communicating in real time over an API | The system needs a live API adapter with queueing and retry, plus recorded sync state per record | rule `STS-1`; adapter not built (needs sponsorship) |
| STS-2 | 64-4.221(4) | Full integration must be achieved **before cultivation authorization** | Integration is the first gate a new licensee faces, ahead of any plant record | rule `STS-2` |
| STS-3a | 64-4.221(3)(a) | Three department-approved training sessions must be completed | Track training dates and completion per MMTC as a prerequisite record | `INTEGRATION_PLAN_REQUIRED` does not cover this; open item |
| STS-3b | 64-4.221(3)(b), (5)(a) | A written integration plan must be submitted to `ommu_seedtosale@flhealth.gov` and approved | Generate the plan pack from operator data, with a checklist per required element | `missing_integration_plan_items()` |
| STS-3c | 64-4.221(3)(c) | A validation process with the department vendor: test files sent from internal STS to department STS | Needs a test-file mode and a validation transcript | not built |
| STS-5b | 64-4.221(5)(b)1-4 | The plan must name: the responsible contact; the internal STS name; milestone dates for UAT credentials, integration start, integration complete; a contingency plan for disconnections and backfill | `INTEGRATION_PLAN_REQUIRED` fields 1-8 | `missing_integration_plan_items()` |
| STS-5b5 | 64-4.221(5)(b)5 | Named employees responsible for integration and its maintenance | Employee records plus role scoping on the API | `model` employee entity, `check_access` |
| STS-5a | 64-4.221(5)(a) | Unique product IDs for current inventory submitted on Form DH5058 with the plan | Unique product ID registry, exportable in DH5058 shape | `model.FinalProduct.unique_product_id`, rule `FORM-4` |
| STS-5c | 64-4.221(5)(c) | The plan may be updated through the variance process (64-4.023) | Versioned plan records with a variance log | not built |
| STS-4 | 64-4.221(6) | Switching internal STS vendor after integration requires a new plan **and** a new validation, before the change | Migration tooling must produce a plan and a validation run, not just an export | design constraint on the cutover kit |
| STS-7 | 64-4.221(7) | Non-compliance is disciplined under 64-4.210, including suspension and revocation | Severity model: integration failures are license-level, not cosmetic | `Severity.VIOLATION` |
| FORM-4 | 64-4.221(1)(c) | One unique product ID per product type, where type = cultivar + size + volume + flavor + THC:CBD ratio + route; a unique SKU may serve | ID assignment rules keyed on those six attributes | rule `FORM-4` |
